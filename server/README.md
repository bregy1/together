# Yaruno server

The Go service of Yaruno (ADR-0004, ADR-0012): REST API from the hand-written contract in `../api/openapi.yaml`, PostgreSQL through pgx v5, ent with Atlas versioned migrations.

## Layout

```
cmd/server/          main: configuration, database pool, HTTP server, graceful shutdown
internal/api/        code generated from ../api/openapi.yaml, with the contract embedded (do not edit api.gen.go)
internal/config/     configuration from environment variables
internal/database/   PostgreSQL pool (pgx v5)
internal/health/     GET /healthz
internal/login/      login codes, device sessions, GET /me (stubs until CR-0001.T11)
internal/signup/     sign-up steps, municipalities, interests (stubs until CR-0001.T12)
internal/photos/     sign-up photos (stubs until CR-0001.T13)
internal/server/     assembles the generated router, the handlers and the middleware
internal/server/session/  session verifier interface and request context; sessiontest/ holds an in-memory fake
internal/testdb/     test helper: database URL or skip
ent/schema/          ent schema (empty until the data model task)
ent/migrate/migrations/  Atlas versioned migrations (empty)
atlas.hcl            Atlas project file
.air.toml            reload on save (development only)
```

## Configuration

| Variable | Default (local development only) | Meaning |
|---|---|---|
| `HTTP_ADDR` | `127.0.0.1:8080` | host:port the server listens on |
| `DATABASE_URL` | `postgres://yaruno@localhost:5432/yaruno?sslmode=disable` | PostgreSQL connection string; holds a password in real deployments, never logged |
| `APP_ENV` | `development`, but only while `HTTP_ADDR` is a loopback address | `development` or `production`. Required as soon as the server listens beyond loopback (for example `:8080` in Docker), so a deployment that forgets it never starts with development behaviour. Development-only features refuse production (NFR-SEC-004) |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:8081` in development | comma-separated browser origins (`scheme://host:port`) allowed to call the API cross-origin, for the Expo web preview (ADR-0009). Development only: setting it with `APP_ENV=production` stops the server |

The configuration is validated at startup; an invalid value stops the server with a message naming the variable (never its value). If the database is not reachable at startup, the server logs a clear error, keeps running and `GET /healthz` answers `503 {"status":"unavailable"}` until the database answers.

## Request handling

`internal/server` mounts the strict server generated by oapi-codegen on `net/http`'s `ServeMux` and wraps it, from the outside in:

1. **Panic recovery:** 500 `internal_error`; the log gets the panic's type and stack, never its value.
2. **Cross-origin access, development only:** origins in `CORS_ALLOWED_ORIGINS` get `Access-Control-Allow-Origin`; their preflight is answered 204 with the methods and the `Authorization` and `Content-Type` headers. In production this layer is not installed: no CORS header is ever sent and a preflight gets 405.
3. **`Cache-Control: no-store`** on every response to an operation that requires a session, to `verifyLoginCode`, and to any request with an `Authorization` header, error answers included.
4. **Request validation** with nethttp-middleware and kin-openapi against the contract embedded in `api.gen.go` (oapi-codegen `embedded-spec`; the binary never reads `../api/openapi.yaml` at run time, and a contract test fails when the embedded copy differs from the file). Operations with the `session` scheme need `Authorization: Bearer <token>`, checked by a `session.Verifier`; until CR-0001.T11 the server runs with `session.RejectAll`, so every signed-in call answers 401.

Every error carries the contract's `Error` body: 400 `request_invalid` (breaks the contract), 401 `unauthenticated` (with `WWW-Authenticate: Bearer`), 404 `not_found` (unknown path), 405 `request_invalid` (with `Allow`), 500 `internal_error`. Neither responses nor logs carry request values: validation failures log only the operation, the field path and the broken rule. The photo parts `image/jpeg` and `image/png` are registered with kin-openapi as plain file data so uploads pass validation; their bytes are checked by the photo handler.

## Commands

Run from `server/` with the 64-bit Go 1.27 first on the `PATH` (bash: `export PATH="/c/Program Files/Go/bin:$PATH"`).

| What | Command |
|---|---|
| Build | `go build ./...` |
| Test | `go test ./...` |
| Test with a database | `DATABASE_URL=postgres://… go test ./...` (never production) |
| Vet | `go vet ./...` |
| Format check | `gofmt -l .` (prints nothing when clean) |
| Generate | `go generate ./...` (Go code from `../api/openapi.yaml`) |
| Validate the contract | `go test ./internal/api/` (kin-openapi loads and validates `../api/openapi.yaml`; generation also fails on an invalid file) |
| Run | `go run ./cmd/server` |
| Run with reload on save | `go install github.com/air-verse/air@v1.67.4`, then `air` |
| Health check | `curl -i http://127.0.0.1:8080/healthz` |

Tests that need PostgreSQL read `DATABASE_URL` and are skipped with a message when it is not set.

## Migrations

ent with Atlas versioned migrations (ADR-0004): timestamped SQL files plus `atlas.sum` in `ent/migrate/migrations/`; a test checks that the directory matches its `atlas.sum`.

- **ent code generation** starts with the first entity: ent refuses an empty schema. The `go:generate` line to switch on is in `ent/generate.go`.
- **Atlas CLI:** Atlas no longer supports `go install`; it is installed as a release binary or used as the `arigaio/atlas` Docker image. Its Community Edition (Apache-2.0) supports `migrate diff`, `apply` and `status` but not `migrate lint`. With the CLI: `atlas migrate diff <name> --env local` and `atlas migrate apply --env local`, with `DATABASE_URL` and `ATLAS_DEV_URL` (an empty scratch database) set. Not yet verified on this machine.
