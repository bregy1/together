# ADR-0007 Internationalisation approach

- **Status:** accepted · **Date:** 2026-11-08
- **Decided by:** the boss · **Prepared by:** Claude, consulted: expo-react-native-expert
- **Affected spec IDs:** `constitution.md` → Languages; `product/glossary.md`; NOTIF (push texts); ONB (SMS text); every area with UI text
- **Supersedes:** — · **Superseded by:** —

## Context

All user-facing text goes through i18n keys from the first line; German is the source, French and English are prepared and must ship by adding translations only; dates, times and numbers follow the user's locale (`constitution.md` → Languages). The app is Expo (ADR-0003); push and SMS texts are written by the Go server (ADR-0005, ADR-0006).

## Decision drivers

1. Keys from day one; new languages without code changes (constitution)
2. Plurals and locale-aware formatting for de-CH, fr-CH and en (constitution)
3. Translations can be updated over the air (ADR-0003)
4. Team fit: TypeScript/React (boss)

## Options

### A) i18next + react-i18next + expo-localization
- **Pros:** the most common choice; type-safe keys via TypeScript resource types; plurals via `Intl.PluralRules` (Hermes supports `Intl`); JSON resources load at runtime, so OTA-delivered translations fit; ICU syntax available through a plugin if translators need it.
- **Cons:** very large resource files can slow type checking.
- **Sources:** https://docs.expo.dev/guides/localization/ (checked 2026-11-08) · https://www.i18next.com/overview/typescript (checked 2026-11-08)

### B) Lingui
- **Pros:** ICU MessageFormat natively, compiled at build time, small runtime.
- **Cons:** extract-and-compile workflow with a Babel plugin; less common.
- **Sources:** https://lingui.dev/introduction (checked 2026-11-08)

### Server texts (push, SMS)
The Go server keeps its own small catalogue with the same keys and languages and renders push and SMS texts in the member's language; the library is chosen with the first NOTIF tasks (small-library approval).

### Comparison

| Driver | A) i18next | B) Lingui |
|---|---|---|
| Keys, new languages without code | meets | meets |
| Plurals, locale formatting | meets (`Intl`) | meets (ICU) |
| OTA translations | meets | meets |
| Team fit | meets | partly (extra tooling) |

**Recommendation (Claude):** A, because it meets every driver with the least tooling and is familiar to a React developer. Would change if translators insist on full ICU syntax everywhere. Reversal cost: medium (all keys stay, call sites change).
**Not verified:** Hermes `Intl` completeness for de-CH, fr-CH and en-CH formats; FormatJS/react-intl was not compared.

## Decision

**Option A: i18next + react-i18next + expo-localization** in the app, and a small server-side catalogue with the same keys for push and SMS texts, decided by the boss on 2026-11-08.

**Reasons (boss):** chose the recommended option.

## Consequences

- **Positive:** keys and type safety from the first screen; French and English ship by adding JSON files, also over the air.
- **Negative and risks:** two catalogues (app and server) must use the same keys and glossary terms; large resource files can slow type checks.
- **Follow-ups:**
  - Project setup: i18next with German as the source, `fr` and `en` prepared, keys typed; a lint or test that fails on hard-coded UI strings.
  - The server catalogue library is approved in a small-library batch with the first NOTIF tasks.
  - NFR-INTL requirements: locale-aware dates, times and numbers for de-CH, fr-CH and en (`/spec-write`, `product/nfr.md`).
