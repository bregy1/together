# How this spec works

> Spec format version: **1.0** (from the `claude-skills` kit). Do not edit this file per project; upgrade it from the kit.

This folder is the **single source of truth** for the app. Everything the app is and does — idea, goals, features, behaviour, design, technical architecture, decisions — is written here. Code is derived from the spec, never the other way around.

- **To change the app, change the spec first.** Then the implementation follows the spec.
- **If something is not in the spec, it is not decided.** Nobody (human or agent) fills a gap with an assumption; it becomes a `[NEEDS DECISION: …]` marker and goes to the boss.
- **Behaviour lives in `product/`, look and feel in `design/`, the how in `tech/`.** Keeping them apart stops technical details from leaking into requirements and keeps each file short.

## Roles

| Role | Who | Owns |
|---|---|---|
| **Boss** | The human owner of the project | All decisions: scope, priorities, trade-offs, tech choices, approvals |
| **Manager** | Claude (main session) | Writing the spec from the boss's answers, planning, dispatching specialist agents, verifying, reporting |
| **Specialists** | Subagents | One task each, with only the spec IDs they need; they return open questions instead of guessing |

## Layout

```
spec/
├── README.md              ← this file (conventions)
├── constitution.md        ← non-negotiables: platforms, locales, quality bars, privacy, ways of working
├── CHANGELOG.md           ← spec version history: spec created, format upgrades, one entry per closed change request
├── product/
│   ├── vision.md          ← idea, problem, goal, target users, success metrics, non-goals, principles, risks; ends with the discovery status
│   ├── app.md             ← identity: name, bundle IDs, permissions + rationale, store listing, legal (platforms and locales live in the constitution)
│   ├── features.md        ← feature map: areas, ID prefixes, MVP cut, status per area
│   ├── journeys.md        ← end-to-end user journeys, referencing requirement IDs
│   ├── glossary.md        ← canonical terms in every UI language
│   ├── nfr.md             ← non-functional requirements (performance, offline, a11y, privacy, security, i18n)
│   └── <area>.md          ← one file per feature area: requirements + scenarios
├── design/
│   ├── direction.md       ← brand, tone of voice, visual direction, references, do/don't
│   ├── tokens.md          ← colours, typography, spacing, radii, elevation, motion
│   └── screens.md         ← navigation map, screen inventory, states per screen
├── tech/
│   ├── architecture.md    ← stack, components, data model, APIs, realtime, push, hosting, environments
│   ├── <topic>.md         ← optional deep dives when architecture.md grows too long
│   └── decisions/
│       └── ADR-NNNN-<slug>.md
└── changes/
    ├── CR-NNNN-<slug>/
    │   ├── proposal.md    ← why, scope, out of scope, type (baseline | change)
    │   ├── delta.md       ← ADDED / MODIFIED / REMOVED requirements (full new text)
    │   └── tasks.md       ← derived implementation tasks (disposable)
    └── archive/           ← closed CRs, moved here as YYYY-MM-DD-CR-NNNN-<slug>/
```

Create files only when they get content. An empty template file is noise.

## IDs

IDs are permanent. Once used, an ID is never reused for something else, even after the requirement is removed.

| Thing | Format | Example |
|---|---|---|
| Feature area prefix | 2–5 capital letters, listed in `product/features.md` | `ONB` (onboarding), `PLAN` |
| Requirement | `<AREA>-<NNN>` | `ONB-003` |
| Scenario | `<REQ>.S<n>` | `ONB-003.S2` |
| Non-functional requirement | `NFR-<CAT>-<NNN>`, category in capital letters only (PERF, OFFL, ACC, PRIV, SEC, INTL, …) | `NFR-PRIV-002` |
| Journey | `J-<NN>` | `J-01` |
| Screen | `SCR-<slug>` | `SCR-plan-detail` |
| Decision record | `ADR-<NNNN>` | `ADR-0004` |
| Change request | `CR-<NNNN>` | `CR-0012` |
| Task | `<CR>.T<NN>` | `CR-0012.T05` |

## Requirement format

Each requirement is one heading in its area file:

```markdown
### ONB-003 Verify phone number
- **Status:** implemented · **Priority:** MVP · **Since:** CR-0001
- **Requirement:** WHEN the user submits a phone number, THE SYSTEM SHALL send a one-time SMS code and show the code entry screen (SCR-onb-code).
- **Rationale:** Phone verification is the minimum proof that an account belongs to a real person.
- **Scenarios:**
  - **S1** Given a valid phone number, when the user taps "Code senden" (`onb.phone.send`), then an SMS code is sent and SCR-onb-code is shown.
  - **S2** Given the SMS provider fails, when the user taps send, then an error with a retry option is shown and no account is created.
- **Depends on:** NFR-PRIV-001
```

Rules:

- **One requirement = one `SHALL`.** Two behaviours are two requirements. That keeps every requirement testable and traceable.
- **The requirement sentence uses EARS** (Easy Approach to Requirements Syntax):
  - Ubiquitous: `THE SYSTEM SHALL …`
  - Event: `WHEN <trigger>, THE SYSTEM SHALL …`
  - State: `WHILE <state>, THE SYSTEM SHALL …` (e.g. *WHILE offline*)
  - Unwanted: `IF <condition>, THEN THE SYSTEM SHALL …` (e.g. *IF location permission is denied*)
  - Optional feature: `WHERE <feature is enabled>, THE SYSTEM SHALL …`
- **Scenarios use Given / When / Then.** Each scenario is proven by at least one test.
- **Behaviour only.** No library names, table names or code in `product/`; those belong in `tech/`.
- **UI text** is referenced by i18n key in backticks. Give the source-language wording (see `constitution.md`) in quotes only where the exact words matter (legal text, key buttons). Canonical terms come from `product/glossary.md`.
- **Priority:** `MVP` · `later` · `idea`.
- **Status lifecycle:**

  | Status | Meaning | May contain `[NEEDS DECISION]`? |
  |---|---|---|
  | `draft` | Being written | Yes |
  | `approved` | Boss approved; ready to implement | No |
  | `implemented` | Built, tested and verified against its scenarios | No |
  | `deprecated` | Removed by a CR; kept for history, ID never reused | No |

## Open points: `[NEEDS DECISION]`

Whenever something is unknown, write a marker instead of guessing:

```markdown
[NEEDS DECISION: How long does a password-reset code stay valid? — options: A) 10 minutes, B) 30 minutes, C) 24 hours — recommended: A, because short-lived codes limit abuse and users request them right before use]
```

- Inside a requirement, markers are allowed only while it is `draft`; a requirement cannot be approved while it contains one. Other spec files (vision, constitution, design, architecture) may carry markers until the boss answers them.
- The manager collects open markers and puts them to the boss as multiple-choice questions, recommendation first.
- The answer is written into the spec, and the marker is removed. Significant answers (tech choices, trade-offs, anything expensive to reverse) also get an ADR.

## How the spec changes

| Situation | Path |
|---|---|
| Requirement not `implemented` and not part of an open CR (even if other requirements in its area are implemented) | Edit in place (`spec-write`). |
| Implementing approved requirements for the first time | Open a **baseline** CR whose delta lists the IDs in scope (no text copied). |
| Changing behaviour that is already `implemented` | Open a **change** CR: the delta holds the full new text. The living spec keeps describing the current app until the CR is closed. |
| Code does not do what the spec says (bug) | No CR. Run `spec-verify`, fix the code. |
| The spec itself was wrong | A change CR. |
| Technical decision | ADR in `tech/decisions/`. If it changes behaviour, it also needs a CR. |

The flow for one CR is `spec-change` (proposal + delta) → boss approves → `spec-plan` (tasks) → `spec-implement` → `spec-verify` (repeat until it reports converged) → `spec-close` (merge the delta into the living spec, mark the requirements `implemented`, add a CHANGELOG entry, archive the CR).

Tasks are derived and disposable. Behaviour is never changed by editing `tasks.md`; it changes in the spec. `tasks.md` also carries the fix rounds that `spec-verify` appends, and a verify log with one line per run.

### Decisions (ADRs) and tech readiness

ADR status (`tech/decisions/ADR-NNNN-<slug>.md`), all set by `spec-decide`:

| Status | Meaning |
|---|---|
| `proposed` | Written with options and a recommendation; waiting for the boss |
| `accepted` | The boss decided; binding for all work |
| `superseded` | Replaced by a later ADR, which it names; kept for history, never deleted |

**Tech readiness.** Accepted ADRs must cover each topic below that a CR's requirements need. For a baseline CR, `spec-change` checks this before approval. For every CR, `spec-plan` checks it before planning.

- app framework
- backend and data storage
- authentication
- realtime and push
- i18n approach
- test tooling

Each topic has a row in `tech/architecture.md`. Both skills use this list and nothing else.

Small libraries don't each need their own ADR. The boss can approve them in a batch through `spec-decide`; they are recorded in the "Approved libraries" table in `tech/architecture.md`. Anything not in an accepted ADR or that table needs approval before it is used.

### Change request status (`proposal.md`)

| Status | Meaning | Set by |
|---|---|---|
| `draft` | Proposal and delta being written; may contain markers | `spec-change` |
| `approved` | Boss approved the proposal and delta | `spec-change` |
| `in-progress` | Implementation has started | `spec-implement` (first dispatched task) |
| `verified` | Latest `spec-verify` run converged; a later non-converged run sets it back to `in-progress` | `spec-verify` |
| `closed` | Delta merged into the living spec, CR archived | `spec-close` |
| `withdrawn` | Abandoned before closing; archived with the reason, nothing merged | `spec-change` |

## Delta format (`changes/CR-NNNN-<slug>/delta.md`)

```markdown
## ADDED
### PLAN-014 Show overlap warning
- **Status:** approved · **Priority:** MVP · **Since:** CR-0007
- **Requirement:** WHEN …, THE SYSTEM SHALL …
- **Scenarios:** …

## MODIFIED
### PLAN-003 Request to join  (was: "Join directly")
…full new text…

## REMOVED
### PLAN-005 Join without approval
- **Reason:** Replaced by host approval (PLAN-003).

## IN SCOPE (baseline CRs only)
- ONB-001 … ONB-009, PLAN-001 … PLAN-006
```

Regression guards (`SHALL CONTINUE TO …` lines for nearby behaviour that must not change) live in the CR's `proposal.md`, not in the delta. `spec-plan` turns them into tests and `spec-verify` checks them.

## Traceability

- **Tests** carry the scenario ID in the test name or a tag: `@spec ONB-003.S2`. Every scenario of an `implemented` requirement has at least one test.
- **Code** may carry `spec: ONB-003` in a comment at the module or function that implements a requirement. It is optional but helps impact scans.
- **Tasks** cite the IDs they cover: `CR-0012.T05 [ONB-003, ONB-004]`.
- `spec-verify` follows these links: requirement → task → test → code. It reports anything **missing**, **partial**, **contradicts** or **unrequested** (code that no requirement asks for).

## Internationalisation

UI languages are listed in `constitution.md`. By default German is the source language and French and English are prepared. All user-facing text goes through i18n keys from the first line of code; there are no hard-coded strings. `product/glossary.md` fixes the canonical term per language, so one concept always has the same word on every screen and in every language.

## Keep it lean

- One file per feature area. Split a file only when it passes about 400 lines.
- No research dumps, no copied code, no restating other files: link by ID instead.
- A short, true spec beats a long, stale one. Stale specs are worse than none, because agents act on them with confidence.
